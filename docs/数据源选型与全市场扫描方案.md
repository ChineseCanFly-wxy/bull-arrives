## 一、数据源决策：选东方财富，不是同花顺

你问「哪个好就用哪个」。直接给结论：

> ### ✅ 主力数据源：**东方财富（Eastmoney）**，通过 `akshare-rs` 接入
> ### ✅ 备用数据源：**腾讯证券**（你现有代码已实现，零成本保留）
> ### 🔸 补充数据源：**新浪财经**（分时 tick / 实时快照兜底）
> ### 🔸 按需增强：**同花顺问财**（**只用于自然语言条件选股**，不做主力数据源）

### 1.1 四个候选源的正面对比

| 维度 | 东方财富 | 同花顺（问财） | 腾讯 | 新浪 |
|---|---|---|---|---|
| **全市场快照** | ✅ 单次请求返回全市场 | ⚠️ 需自然语言查询，分页 100/页 | ⚠️ 需按批拼接 | ⚠️ 需按批拼接 |
| **是否需要登录 Cookie** | ❌ 不需要 | ✅ **必须**（7~30 天过期） | ❌ 不需要 | ❌ 不需要 |
| **是否有动态令牌** | ❌ 无 | ✅ **有 `hexin-v`，需执行 JS 生成** | ❌ 无 | ❌ 无 |
| **风控/封禁风险** | 低 | **高**（建议间隔 ≥2s） | 低 | 低 |
| **纯 Rust 实现** | ✅ `akshare-rs` 已覆盖 | ❌ 需自己移植 JS 算法 | ✅ 已有 | ✅ `akshare-rs` 有 |
| **数据质量** | 与同花顺同级 | 同花顺本体 | 同级 | 同级 |
| **ST / 新股分类** | ✅ 有专门接口 | ✅ | ⚠️ 需自己判断 | ⚠️ |
| **资金流 / 龙虎榜** | ✅ 强项 | ✅ | ⚠️ 弱 | ⚠️ 弱 |
| **板块/概念数据** | ✅ 强项 | ✅ 强项 | ⚠️ | ⚠️ |

### 1.2 为什么同花顺只能当「补充」而不能当主力

不是说同花顺不好，而是**工程可靠性差一个数量级**：

1. **`hexin-v` 令牌是前端 JS 动态生成的**。`pywencai` 这个 Python 库为了算这个令牌，内部**要启动 Node.js 执行 JS**。你在 Tauri 里要么内嵌 JS 引擎（`boa_engine`），要么开隐藏 WebView2 窗口——两条路都能走通，但都是额外复杂度。
2. **Cookie 7~30 天过期**。一旦系统的主力链路挂在这个上面，过期当天你的「AI 盯盘」直接瘫痪，而用户根本不知道发生了什么。
3. **有风控限流**。全市场扫描如果走问财，几百次分页请求必然触发封禁。

**但是**——问财有一个能力是东财没有的，而且是「AI 原生」的：

> 🔥 **用中文自然语言描述选股条件，直接返回结构化结果。**
> 例如：「今日放量突破20日均线且市盈率小于30且主力资金净流入的股票」

这个能力正好匹配你「**让 AI 自己拟定条件**」的想法。所以正确姿势是：

```
东财（主力）→ 承担 95% 的数据获取：快照、K线、资金流、财务、板块
问财（补充）→ 只承担「AI 语义选股」这一个场景，且失败可降级
```

> ⚠️ **实测踩到的三个坑（2026-09-12 验证，动手前必读）**
>
> **1. `akshare-rs` 的 `stock_zh_a_spot_em()` 拿不到全市场 —— 只返回 100 条。**
> 源码里它向 `clist_spot_fetch(...)` 传了 `"5000"` 作为 `pz`，但 `util::eastmoney_clist_params`
> 只发 `pn=1`（硬编码第一页），而东财服务端又把单页锁死在 100 条。
> 实测结果：返回 100 条且**全是北交所 920xxx**（降序排列的第一页），完全不可用于全市场扫描。
> → **方案 A（推荐）**：自己用 `reqwest` 写东财适配器 + 分页循环。项目本来就有
> `shared_client()` 和 `sina.rs` / `tencent.rs` 直连适配器的先例，风格一致。
> → **方案 B**：仍用 `akshare-rs`，但只用于**单标的接口**（K线、资金流、财务、龙虎榜、交易日历、`ta` 指标），
> 这些不受分页影响。
>
> **2. 关于 `stock_cy_a_spot` / `stock_sh_a_spot` / `stock_bj_a_spot` 等分板块接口**
> 它们同样传 `pz=5000`，因此**同样会受 100 条上限影响**，不要指望它们绕过分页。
>
> **3. `akshare-rs` 是 v0.1.14 早期版本（月下载量约 300）**
> **务必把它包在自己的 `DataSource` trait 后面**，这样接口坏了可以随时切换成直连实现。
>
> ✅ **另外两个好消息**
> - `akshare-rs` 默认 **30s 超时且不读环境代理**（`AkShareClient::new()`），而东财是国内源，**不走代理反而更稳**；
>   需要代理时可用 builder：`AkShareClient::builder().proxy(...).user_agent(...).build()`
> - 实测编译约 3 分钟（release），依赖树偏大但可接受；返回字段齐全，
>   含 `volume_ratio`（量比）/ `turnover_rate`（换手）/ `total_market_cap` / `pe_dynamic` 等，
>   **L0→L2 零额外请求的设计成立**

## 二、必须先澄清的一件事

你说想「**分析所有大 A 的股票**」。这里有个认知需要校正，否则方案会跑偏：

> ❌ **「让 AI 分析全市场 5400 只股票」在成本和技术上都不成立。**
> LLM 每次分析要几万 token、几秒到几十秒。5400 只 × 哪怕每天 1 次 = 成本爆炸 + 几小时延迟。

正确的心智模型是：

> ✅ **代码负责「分析全市场」，AI 负责「解读少数」。**
> 技术指标、因子打分这类确定性计算，代码一天跑 5400 只毫无压力（CPU 几秒钟的事）。
> AI 只在漏斗最后剩下的 5~15 只上做深度解读——这才是 AI 该待的位置。

**你直觉是对的**：「限定条件下来一天获取量其实还好」——确实还好，而且是**关键**。所以下面这套漏斗设计就是围绕你这个想法做的。

## 三、五层漏斗：全市场扫描的可行架构

```
L0  全市场快照        ~5,400 只   ← 1 次 HTTP 请求，~1-2 MB
     ↓  硬过滤（设置里的限定条件）
L1  基础池            ~2,500 只   ← 0 额外请求（快照字段就够）
     ↓  量价粗筛（纯代码）
L2  候选池            ~150 只     ← 0 额外请求（同上）
     ↓  因子精算（需拉日K）
L3  重点池            ~30 只      ← ~150 次请求（限速）
     ↓  AI 深度分析
L4  AI 结论池         ~8 只       ← ~8 次 LLM 调用
     ↓  规则校验 + 分级推送
L5  提醒
```

### 3.1 逐层说明

#### L0 · 全市场快照（这是可行性的基石）

> ✅ **已实测验证（2026-09-12）**
> 东财 `push2.eastmoney.com/api/qt/clist/get` 返回 `data.total = 5913`，
> 但 **单页硬上限被锁死在 100 条**（实测 `pz=500` / `pz=1000` 均只返回 100 条）。
>
> **所以：全市场快照 = 60 次分页请求**（5913 ÷ 100），不是一个请求。
> 分页参数 `pn=1..60` 实测正常，最后一页 13 条，与总数完全吻合。
>
> 单页约 10KB（5 字段）～ 25KB（25 字段），60 页合计约 **0.6～1.5 MB**。
> 串行约 6-10 秒，**并发 5-6 路后约 1-2 秒** —— 结论仍然完全可行，只是要写分页循环。

单行字段（足够做两层筛选）：
```
代码 / 名称 / 现价 / 涨跌幅 / 涨速 / 5分钟涨跌 / 60日涨跌 / 年初至今
成交量 / 成交额 / 振幅 / 最高 / 最低 / 今开 / 昨收
量比 / 换手率 / 市盈率(动) / 市净率 / 总市值 / 流通市值
```

**用这套字段能零成本完成 L1 + L2 的全部判断。**

#### L1 · 硬过滤（用户设置的条件）

纯内存筛选，不做任何网络请求。典型输出 5,400 → 2,500。

#### L2 · 量价粗筛（纯代码）

仍然只用 L0 字段：涨跌幅区间、量比下限、换手率区间、振幅、市值排序、涨幅排名前 N。
典型输出 2,500 → 150。

> 💡 **L0→L2 全程零额外请求**，这就是为什么「全市场扫描」真的可行。

#### L3 · 因子精算（需要拉日K）

到这里才需要逐只拉日 K 线。150 只 × 1 次请求，配合限速（如 200ms/次）约 30 秒完成。

计算内容：
- 技术指标（趋势/动量/位置/量价）→ 用 `akshare::ta`
- 形态识别（突破、回踩、缩量整理、放量启动）
- 关键位（支撑/压力）→ 近 N 日高低点、均线、筹码密集区
- 因子打分 → 合成分数排序

典型输出 150 → 30。

#### L4 · AI 深度分析（成本敏感区）

只对 30 只里的**前 8~15 只**跑多 Agent 分析。这是唯一花钱的一层。

#### L5 · 规则校验与推送

AI 给出的结论必须过规则引擎（止损止盈、仓位、置信度门槛）才推送。

### 3.2 时间预算（盘中一次完整扫描）

| 层 | 耗时 |
|---|---|
| L0 快照（60 页分页，并发 6） | ~1-2 秒 |
| L1 + L2 内存筛选 | < 100 毫秒 |
| L3 拉 150 只日K（限速） | ~30-40 秒 |
| L4 AI 分析 10 只（并发 3） | ~60-120 秒 |
| **合计** | **约 2-3 分钟** |

所以**盘中每 5 分钟扫一次**是舒服的节奏。快照高频（如 30 秒）也完全可以——L0 虽然要 60 页，但并发后仅 1-2 秒。

## 五、AI 动态拟定条件（你这个想法很好，但要加护栏）

### 5.1 为什么这个想法是对的

固定阈值有个天然缺陷：**市场状态不同，有效阈值完全不同。**

- 单边上涨行情：涨幅下限设 3% 会选出一大堆，噪音高
- 震荡市：涨幅下限设 3% 会选不出东西
- 普跌行情：所有股票都在跌，"站上 MA20" 的条件可能只剩几十只

**让 AI 根据昨日市场状态动态调整阈值，是真正有附加值的设计。** 而且它天然可验证。

### 5.2 机制设计

```
每日盘前（如 09:00）
├─ 输入：昨日市场状态快照
│   ├─ 涨跌家数、涨停/跌停数、炸板率
│   ├─ 指数状态（位置、量能、均线关系）
│   ├─ 板块轮动（领涨/领跌板块、板块资金流）
│   ├─ 北向资金流向
│   └─ 昨日 AI 筛选参数的实际效果（命中率、次日表现）
│
├─ AI 输出（严格 JSON Schema，不是自由文本）
│   {
│     "market_regime": "震荡偏强",
│     "reasoning": "……（200字以内）",
│     "params": {
│        "change_pct_min": 2.0,      // 涨幅下限
│        "change_pct_max": 7.5,      // 涨幅上限
│        "volume_ratio_min": 1.8,    // 量比下限
│        "turnover_min": 1.5,        // 换手率下限
│        "turnover_max": 15.0,
│        "market_cap_min": 50,       // 亿
│        "market_cap_max": 1000,
│        "require_above_ma20": true,
│        "require_fund_inflow": true,
│        "board_weight": {"创业板": 1.2, "科创板": 0.9, "上证主板": 1.0}
│     },
│     "focus_sectors": ["AI算力", "电力设备"],
│     "avoid_sectors": ["白酒"],
│     "confidence": 0.68
│   }
│
├─ 硬护栏校验（关键！）
│   ├─ 参数必须落在用户设定的「安全区间」内
│   │   例：涨跌幅下限只能在 0~5 之间，AI 想设 8 会被夹到 5
│   ├─ 禁止关闭硬性排除项（ST / 退市 / 停牌）
│   ├─ 禁止把候选池撑爆（若 L2 输出 > 500 只，自动收紧）
│   └─ 校验失败 → 降级为「昨日参数」或「预设默认」
│
├─ 落库：ai_filter_params(date, params, reasoning, market_snapshot)
│
└─ 按用户策略执行
    ├─ 自动应用（用户信任模式）
    ├─ 需确认（弹窗展示 AI 的条件与理由，用户一键采纳/修改）
    └─ 仅建议（只记录不应用）
```

### 5.3 必须有的评估闭环

**这是让「AI 调参」从玄学变成能力的关键：**

```
每日记录：AI 参数 → L2/L3 输出 → L4 结论
次日核对：这些结论的实际表现（涨了没、涨多少、有没有触发止损）

周期性统计：
├─ AI 调参组 vs 固定阈值组：哪组选出的标的次日表现更好？
├─ AI 的 market_regime 判断是否准确？（它说"震荡偏强"，实际是否如此？）
├─ AI 的 focus_sectors 是否真的领涨？
└─ 若连续 N 周 AI 组不如固定阈值 → 自动降级为固定阈值，并提示用户
```

没有这个闭环，「AI 调参」就是个不可证伪的黑盒，用久了你自己都不知道该不该信它。

### 5.4 建议的默认策略

**前 4 周用「仅建议」模式。**
只记录 AI 的参数建议和实际效果，不真正应用。攒够样本后再判断 AI 调参是否值得信任。这比一上来就让它改你的筛选条件要稳得多。

## 六、成本与流量实测估算

这部分给你个底，让你知道「一天获取量」到底是什么量级。

### 6.1 数据流量

| 项目 | 单次体积 | 频次 | 日总量 |
|---|---|---|---|
| L0 全市场快照 | ~1.5 MB | 盘中 48 次（5分钟） | **~72 MB/天** |
| L3 日K（150 只） | ~3 KB/只 | 每次扫描 1 轮 | ~0.5 MB/轮 |
| 日K 历史回填（首次） | — | 一次性 | **~200-300 MB** |
| 日K 日增量 | ~2 KB/只 × 5400 | 每日 | **~11 MB/天** |
| 财务/资金流 | 少量 | 每日/每周 | < 5 MB/天 |

**结论：除首次回填外，日常流量约 100 MB/天量级。完全不是问题。**

> 🔧 **优化建议**：L0 快照不必全部落库，**只落 L1/L2 过滤后的结果**（~150 行/轮），
> 这样 SQLite 增长极慢，查询也快。全量快照只保留「当日最新一份」用于回溯。

### 6.2 LLM 成本

| 环节 | 单次消耗 | 频次 | 日消耗 |
|---|---|---|---|
| 盘前参数拟定 | ~8K in / 1K out | 1 | 8K / 1K |
| 盘中 L4 深度分析 | ~20K in / 2K out | 每次扫描 10 只 × 8 轮 | 1.6M / 160K |
| 盘后复盘 | ~30K in / 3K out | 1 | 30K / 3K |

**盘中是成本大头。** 三个必做的降本措施：

1. **分级模型**：L2 粗筛用便宜小模型（甚至纯规则），L4 才用大模型
2. **信号去重**：同一只股票当天已分析过且无新信号 → 跳过
3. **结果缓存**：同标的同参数 15 分钟内不重复调用

做完这三条，典型成本可降到「一天几毛到几块钱」，完全可接受。

### 7.2 数据源 trait 扩展

现有 `DataSource` trait 主要面向「单只股票的行情」。需要**平行**加一个面向全市场的 trait，而不是硬塞进去：

### 7.3 其他要点

| 要点 | 做法 |
|---|---|
| **限速** | L3 逐只拉 K 线必须串行 + 固定间隔（200~300ms），并做 429/超时重试退避 |

## 十、分时形态库（对应你提供的那三张 KMeans 图）

### 10.1 那三张图在做什么

用 KMeans 把 **5,291 个交易日**的**分时（日内）走势**，尺度归一化后聚成 **6 / 16 / 32 类**；
每类给出均值轨迹 + ±1σ 灰带，并标注样本数、跳空幅度、日内涨跌幅、极值出现时刻。

以 k=6 为例（样本合计正好 5291，聚类是完整的）：

| 形态 | 样本 | 占比 | 跳空 | 日内 | 走势特征 |
|---|---|---|---|---|---|
| 0 | 768 | 14.5% | +0.19% | **+2.26%** | 早盘下探至 11:03，之后单边上行 |
| 1 | 641 | 12.1% | +0.17% | **-6.84%** | 全天单边下行，14:43 最低 |
| 2 | 1264 | **23.9%** | +0.25% | **-3.63%** | 高开低走，全天阴跌 |
| 3 | 403 | 7.6% | -0.37% | **+7.60%** | 快速拉升后横盘，尾盘继续走高 |
| 4 | 1061 | 20.1% | -0.21% | -1.25% | 早盘 09:46 冲高后回落震荡 |
| 5 | 1154 | **21.8%** | -0.21% | **+3.46%** | 低开高走，09:30 最低，震荡上行 |

上涨形态（0/3/5）合计 43.9%，下跌形态（1/2/4）合计 56.1%。

### 10.2 判断：有用，而且比让 AI 拍脑袋预测靠谱得多

**✅ 价值所在**
- 这是「历史会重演」假设的**可计算版本**，完全确定性、无幻觉、可回测
- 提供了「当前走势 → 历史同类 → 后续分布」的推理路径，天然适合做盘中提醒
- 5,291 个样本在统计上足够支撑 k=6~16 的聚类

**⚠️ 但缺了最关键的一步，还有五个坑**

1. **只有「分类」，没有「预测」。**
   图里完成了形态归类，但**没有统计形态 → 后续收益分布**。
   必须补上：「形态3 出现后，次日上涨概率 X%、平均收益 Y%、最大回撤 Z%」。
   **没有这一步，形态库只是描述性统计，没有交易价值。**

2. **样本是「单个标的」的 5291 个交易日（≈21 年）。**
   如果这是上证指数 / 沪深300，那么形态库**只适用于该指数，不能直接套到 5400 只个股**。
   个股有涨跌停约束、流动性差异、主力行为，日内形态分布与指数完全不同。
   → **形态库必须按标的类型分层建立**（或至少按板块 + 市值分层）。

3. **「跳空方向」与「日内方向」经常相反 —— 这本身是个有价值的发现。**
   k=6 里：形态2 高开却收 -3.63%，形态3 低开却收 +7.60%，形态5 低开却收 +3.46%；
   反向 4 个 vs 同向 2 个。**A 股日内有明显的「反向/均值回复」特征**，
   这可以直接做成一个独立因子（跳空幅度 → 日内反转概率）。

4. **k=32 明显过拟合。**
   最小类只有 **25 个样本（0.5%）**，统计上不可靠，而且看起来是把连续形态硬切成碎片。
   → **可用的是 k=6 ~ 16**，其中 k=6 最稳、最可解释。

5. **实时匹配是核心工程难点。**
   盘中 10:30 时只有半条轨迹，**不能用完整日形态去匹配**。
   必须做**按时间截断的形态匹配**：用 09:30–10:30 的片段，去和历史上「同期（09:30–10:30）片段」比。
   → 这决定了它能不能变成「盘中提醒」，而不只是盘后统计。

### 10.3 算法可以升级（一个具体建议）

图里用的是 **KMeans + 欧氏距离**。两个更好的选择：

| 算法 | 为什么更好 |
|---|---|
| **k-Shape** | 用**互相关（cross-correlation）**而非欧氏距离做距离度量，对时间轴平移/伸缩更鲁棒，是**专为时序形态聚类设计**的算法。SIGMOD 2015 最佳论文 |
| **Matrix Profile（stumpy）** | **不需要预设 k**，直接发现「反复出现的形态」（motif discovery），比聚类更贴近「找有价值的形态」这个目标 |

### 10.4 最值得参考的开源项目

> ⭐ **`fengyi1999/Sequoia3` —— 形态选股系统**
> Python A 股形态选股系统，用 **DTW + K-Shape** 做形态匹配，AKShare 取数（主板/创业板/科创板），
> **「用户可选择标准形态，匹配全市场约 5000 只股票，按匹配度输出结果」**。
> 这几乎就是你那三张图思路的**完整工程实现**，是最直接的参考对象。

其他值得看的：

| 项目 | 借鉴点 |
|---|---|
| `thedatumorg/kshape-python` | k-Shape 官方 Python 实现（含论文与基准数据） |
| `adam-dziedzic/kshape` | k-Shape 的 PyTorch GPU 版，大规模聚类时更快 |
| `TDAmeritrade/stumpy` | Matrix Profile，做 motif discovery |
| `wannesm/dtaidistance` | DTW 高性能实现 |
| `microsoft/qlib` | 要上真正的机器学习预测模型（GBDT/LSTM）时的参考 |

### 10.5 落地到你的项目：形态库放在哪一层

形态库应该建在 **L3（因子精算）之上、L4（AI 分析）之下**：

```
盘后：当日全量分时入库 → 归入已建立的形态类
      → 统计该形态的历史后续收益分布（这一步是灵魂）
      → 更新「形态 → 期望收益/胜率」查找表

盘中：实时取当前已走出的分时段（如 09:30–10:30）
      → 与历史同期片段匹配（不是完整日）
      → 命中高价值形态 → 进入 L4 让 AI 结合资讯解读
      → 规则校验后推送提醒
```

**关键设计：形态库要按「板块 × 市值」分层建立，不要用一个全局形态库。**
指数形态、主板白马、创业板题材股、科创板新股，四者的日内形态分布完全不同。

**具体的节流建议（基于实测的限流阈值反推）：**

| 场景 | 建议频率 |
|---|---|

- **盘中只拉「变化敏感的字段」**，或者
- **只在关键时点拉全量**（09:35 / 10:30 / 11:25 / 13:05 / 14:00 / 14:50 六个时点），
  其余时间只轮询自选股（几十只，量小）

## 十二、数据层架构：akshare 到底怎么用（已落地）

### 12.1 结论先行：不是二选一，而是分层

你问「akshare 好用的话有办法用吗」——**有，而且官方就给了答案**。但正确的做法不是「选一个」，而是**按数据的使用频率分层**：

| 数据 | 特征 | 方案 |
|---|---|---|
| **全市场快照 / K线 / 分时** | 高频、量大、对延迟敏感 | ✅ **Rust 自建**（已完成） |
| **财务 / 龙虎榜 / 涨停原因 / 概念板块 / 分红** | 低频、长尾、格式复杂 | ✅ **AKTools（本地 HTTP）** |

理由：高频接口自己写，才能控制限流、缓存和性能；长尾接口几十上百个，逐个 Rust 化是纯粹的浪费。

### 12.2 AKTools 是什么（akshare 官方出品）

官方描述：

> *"AKTools is an elegant and simple **HTTP API library for AKShare**, built for AKSharers!
> 通过 AKTools 可以利用一行命令来启动 HTTP 服务，从而让原本专属服务于 Python 用户的开源财经数据接口库 AKShare 的使用**突破编程语言的限制**。无论您使用的是 C/C++、Java、Go、**Rust**、Ruby、PHP、JavaScript、R、Matlab、Stata 等编程语言或软件都可以快速、轻松获取财经数据。"*

**用法（三步）：**

```bash
pip install aktools
python -m aktools                 # 启动服务，默认 http://127.0.0.1:8080
```

然后 akshare 的接口名直接当 URL 路径用：

```
http://127.0.0.1:8080/api/public/stock_zh_a_hist?symbol=600000&period=daily&adjust=qfq
http://127.0.0.1:8080/api/public/stock_board_concept_name_em
http://127.0.0.1:8080/api/public/stock_lhb_detail_em
```

**它把 akshare 的 1000+ 接口全部变成 HTTP 接口**，返回 JSON。README 里甚至有 Rust 的调用示例。

### 12.3 三条路线的真实成本对比

| | Rust 自建 | akshare-rs | **AKTools** |
|---|---|---|---|
| 接口覆盖 | 你写多少算多少 | v0.1，部分不可用 | **akshare 全部 1000+** |
| 安装包体积 | **+0** | +0 | **+150~250MB**（需带 Python + pandas） |
| 冷启动开销 | **0** | 0 | +2~5 秒（import pandas 很慢） |
| 分发复杂度 | **低** | 低 | 高（sidecar 进程要管生命周期/端口/崩溃重启） |
| 上游改版时 | 你要改代码 | 等作者发版 | **等 akshare 发版即可** |
| 适合 | 高频核心接口 | 单标的简单数据 | **长尾/探索期** |

> **关键取舍**：AKTools 用「安装包体积 + 启动时间」换「数据覆盖率 + 维护成本」。
> 对一个桌面应用来说，250MB 不是不能接受，但**不该为核心功能付这个代价**。

### 12.4 推荐架构：可插拔 Provider

**不要让业务层知道数据从哪来。** 定义统一的 provider 抽象：

```
业务层（筛选 / 分析 / AI）
        ↓ 只依赖 trait
┌──────────────────────────────────────┐
│  MarketDataSource trait              │
├──────────────────────────────────────┤
│ ① EastmoneyNative  ← Rust 自建 ✅已做 │  高频：快照/K线/分时
│ ② AkToolsSidecar   ← 本地 HTTP       │  长尾：财务/龙虎榜/概念
│ ③ AkShareRs        ← 纯 Rust（备选）  │  单标的
│ ④ Tencent / Sina   ← 已有，兜底       │  容灾回退
└──────────────────────────────────────┘
```

**分阶段推进：**

| 阶段 | 做法 |
|---|---|
| **现在（开发期）** | 跑 AKTools 本地服务，快速把数据能力铺开，**验证哪些数据真正有用** |
| **中期（产品化）** | 把验证过的高频接口逐个 Rust 化；AKTools 退化为「可选增强包」，用户想用长尾数据时装 |
| **长期** | 只保留 Rust 实现 + 可选 sidecar |

**这个架构的好处：不锁定任何一条路。** 万一 akshare 挂了，或者你想砍掉 Python 依赖，换一个 provider 即可，业务代码零改动。

### 12.5 本轮已落地的代码（已编译验证）

| 文件 | 内容 | 验证状态 |

| `src-tauri/src/datasource/eastmoney_universe.rs` | 全市场快照（60 页分页 + 6 路并发）、22 字段行结构、板块/ST/退市/停牌/一字板分类、**带 TTL 缓存 + 请求去重 + 陈旧数据兜底**、**L1 筛选引擎** | ✅ 13 个单测全部通过 |
| `src-tauri/src/commands/universe.rs` | 命令 `get_market_universe(filter, limit, force_refresh)` | ✅ 编译通过 |
| `datasource/mod.rs` / `commands/mod.rs` / `lib.rs` | 模块声明与命令注册（各 +1 行） | ✅ `cargo check --all-targets` 通过 |

**该模块的两个关键设计：**

1. **专用 no-proxy Client**。没有复用 `datasource::shared_client()`，因为后者**没有设置 `.no_proxy()`**，
   而东财请求一旦走系统代理就会被 TLS 切断（实测）。用独立 Client 既解决问题，又**不影响现有 sina/tencent 适配器**。
2. **缓存 + 请求去重**。全市场一轮是 60 次请求，缓存 TTL 默认 60 秒；
   用 `RwLock` 写锁串行化，保证并发调用时**只有一次真实拉取**，这是防限流的关键。
