# 发布流程

本文是维护者和代码助手的执行约定。用户明确说「发版」时，按本流程完成提交、推送、GitHub 打包与正式 Release，并返回发布链接和验证结果。仅说「整理发版流程」不授权提交或发布；版本号以用户指定版本或准备命令为准。

## 首次准备

- 核对 `origin` 为本项目仓库，并具备 main、标签与 Release 写权限；通过 `gh auth login` 登录，使用 `gh auth status` 验证。登录凭据不写入代码或日志。
- 在 GitHub 仓库 Actions Secrets 配置 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`（无密码密钥的密码可为空）。继续使用与 `src-tauri/tauri.conf.json` updater 公钥匹配的原密钥，不为一次发版随意换钥。私钥文件及内容不得提交。
- GitHub Actions 启用且有构建额度；工作流需要 `contents: write`，自动使用 `GITHUB_TOKEN`，无需提交个人 Token。
- 本地安装 Node.js 22、Rust 和相应平台构建依赖；Windows 优先测试，保留 Windows x64、macOS universal、Linux x64 的 GitHub 构建矩阵。

## 准备一个版本

1. 读取 Git 状态、当前分支和远端。审阅已有未提交改动，保留用户工作；判断这次发布是否包含它们，不能遗漏新功能依赖文件。不要 `git add .`、重置工作区或覆盖本地旧安装 EXE；StockDB 保持只读。
2. 用户未指定版本时，将当前版本递增一个补丁号；例如 2.2.6 → 2.2.7。先检查本地/远端标签与 Release，不重复使用已发布版本。
3. 在 `CHANGELOG.md` 顶部 `## Unreleased` 内归纳实际改动，并同步 README 和必要技术说明。更新说明必须有 `### 分组` 及 `- 条目`，不要记录尚未实现或未经验证的效果。
4. 执行准备命令（下列版本仅为示例）：

```bash
npm ci
npm run release:prepare -- 2.2.7
npm run release:check
npm run build
npm run test:rust -- --lib --locked
```

`release:prepare` 同步 `package.json`、`package-lock.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`、`src-tauri/tauri.conf.json` 五处版本，并把非空 Unreleased 转为带 Asia/Shanghai 日期的版本说明；它不提交、不推送。`release:check` 检查版本、更新说明、编译源文件与大文件，只是静态门槛，不能替代构建和适用测试。改动涉及专项检查时一并执行；GUI 未测要如实注明。

5. 检查 `git diff --check` 和最终 diff。源码依赖的 runner、registry、少量 `include_str!` / `include_bytes!` 证据及测试输入必须进入 Git；大型行情矩阵、供应商原始响应、模型缓存、回放输出、用户数据库、日志和密钥不得进入 Git。大文件检查发现例外时逐项处理，不能关掉门槛强行发布。
6. 按明确路径暂存本次发布文件，检查 `git diff --cached --stat` 与暂存内容后提交。再次执行 `npm run release:check -- vX.Y.Z --tracked`，确保 GitHub 从提交检出时具备全部编译文件。

## 提交、推送和打标签

以下命令在确认干净的发布提交位于 main、检查通过后执行；暂存路径必须来自已审核文件，不能照抄成全部仓库。

```bash
git add <已审核的发布文件路径>
git diff --cached --stat
git commit -m "release: v2.2.7"
git push origin main
git tag -a v2.2.7 -m "Release v2.2.7"
git push origin v2.2.7
```

标签必须指向包含同版本 CHANGELOG、五处版本及全部依赖文件的发布提交。若远端 main 与本地存在分歧，先保留工作并解决，不强推、不盲目合并。

推 `vX.Y.Z` 标签触发 `.github/workflows/release.yml`。手动触发时选择 main 上的工作流，填写已推送的 `tag`；工作流会检出该标签。它只用于未正式发布版本的同提交重试，不代替提交和标签。

若三平台构建已成功、只有发布校验失败，可填写原运行编号 `verify_run`：工作流先核对该运行对应同一标签提交且三项构建成功，再复用草稿中的安装包执行全部验包与签名校验。只修发布工作流时提交到 main 即可，保留已验证标签和安装包；草稿元数据按固定 Release ID 读取，避免草稿按标签查询返回 404。验包工具使用发起工作流的提交，应用构建仍绑定版本标签；工具会再次核对版本、公告和应用更新公钥，允许修复发布工具后重试而不重打安装包。

## 等到 GitHub 完成

工作流先创建草稿 Release，各平台上传产物；只有全部构建与产物检查成功才正式发布。执行助手需观察对应标签/提交的本次运行，不能只看到工作流开始就报成功。

完成条件：

- Windows x64、macOS universal、Linux x64 构建全部成功，发布 job 成功。
- Release 为对应 `vX.Y.Z`，不是草稿或预发布，指向正确发布提交。
- Windows 安装包、便携 ZIP、macOS/Linux 安装产物存在且非空；便携包包含主程序及 `portable.dat`，不带维护者的 `data/`。
- 更新包及对应签名存在；`latest.json` 可下载，版本正确、平台条目完整，URL 指向本版实际产物，签名附件一致，且通过原生 minisign 与应用公钥的密码学校验。
- `SHA256SUMS.txt` 与实际产物一致；发布前核验便携 ZIP 的主程序、标记、文档、x64 PE 和 CRC，拒绝用户数据及路径穿越。
- Release 正文与 `latest.json` 的 notes 都含本版分组及条目；两者来自同一份 CHANGELOG，不能靠事后仅修改 Release 正文修复更新说明。

最后回报版本号、提交、标签、Release 链接、产物及验证情况。安装包已生成与原生 GUI 已验证是两件事，分别说明。

## 失败处理

GitHub 构建失败时读日志并修复，继续跟进到成功或明确阻塞。临时服务错误可重跑同一提交；需要代码修复时提交修复并使用新的补丁版本，旧标签保留。不覆盖/强推已存在的远端标签，不把失败草稿设成最新版本，不降级缺失签名检查。认证或 Secrets 缺失时明确指出需要配置的项，不输出秘密内容，不声称已发布。

## 研究功能的分发边界

研究程序源码随 Git 发布；冻结模型及研究快照由 `research-assets.json` 固定 GitHub Release 附件与 SHA256，CI 下载核验后用 `scripts/research-bundle.py prepare` 构建完整 `research-runtime`。安装包和便携包都包含匹配的独立 Python 与固定依赖，无需用户另装 Python 或填写 CI 路径。发布前必须用实际随包 Python 验证全部冻结文件、年度模型加载与预测，再从全新安装目录执行真实研究任务。大型数据及模型二进制不直接进入 Git 历史，用户纸上账户、个人数据、StockDB 引擎与数据库不随包；StockDB 由用户自行安装。研究更新仍须取得日期与覆盖合格的真实行情，缺数据停用，不得重标旧评分。保留自定义研究环境和受信指纹校验，不纳入已弃用的实战 B 表策略。


源码检出后、首次原生打包前，需要 Python 3.12 与 uv 0.12.7，按锁定附件准备运行资源（GitHub Actions 已自动执行）：

```bash
gh release download research-assets-2026-09-30 --pattern bull-arrives-research-2026-09-30-v2.zip --dir src-tauri/target/research-assets
python scripts/research-bundle.py prepare src-tauri/target/research-assets/bull-arrives-research-2026-09-30-v2.zip src-tauri/target/research-runtime
```

准备命令核对附件与每个冻结文件的 SHA256，再安装匹配依赖并实际预测全部模型；已有输出目录会拒绝覆盖。用户下载正式安装包或便携包时无需执行这些开发步骤。近期主线观察使用在线前复权日线；多年历史ST与原始买卖价位研究仍需StockDB。历史公司行动PDF只用于核算冻结回放中的分红、送转及到账日期，当前资讯和公告由在线接口采集。
