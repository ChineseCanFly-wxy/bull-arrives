## 0. 结论先行

**整体可行，而且你的项目起点比大多数同类项目好得多。** 原因：

- 后端已经是 `DataSource` trait + `DataSourceManager` 的可插拔结构 → 加同花顺/东财只需再写一个适配器
- 已有 `market_clock.rs` 交易时段状态机 → **盘前/盘中/盘后三态调度闸门是现成的**，这是做「定时盯盘」最难啃的骨头之一，你已经有
- 已有 `tauri-plugin-notification` + 托盘 + 置顶行情条 → 提醒通道完整
- 已有 SQLite 三表 + 事件驱动前端 → 落库和推送链路都通

**但有一件事必须先说清楚（很重要，免得后面踩坑）：**

> 「通过一些胜率比较高的模型去预测个股走势」——**可持续的高胜率预测并不存在**。
> 公开数据 + 常规模型能做出的是「概率略优于随机 + 严格风控」，而不是「80% 胜率稳赚」。
> 任何宣称高胜率的回测，绝大多数是前视偏差（用了未来信息）、幸存者偏差或过拟合。
>
> 所以本方案的核心不是「追求高胜率」，而是**三件事**：
> 1. **概率化**：输出「上涨概率 62%，期望收益 +3.1%，最大不利偏移 -2.4%」而不是「会涨」
> 2. **可验证**：每次预测落库，次日自动比对，统计真实胜率与校准曲线
> 3. **守纪律**：止损止盈、仓位上限由规则强制执行，AI 无权绕过
>
> 这样即使模型只有 53% 胜率，配合盈亏比和纪律，长期也能是正期望。这才是量化真正赚钱的逻辑。

## 3. 总体架构：六层

```
┌─────────────────────────────────────────────────────────────┐
│ ⑥ 展示层  Vue + Pinia                                       │
│   AI 对话面板 │ 信号卡/预警中心 │ 预测复盘看板 │ 设置页      │
├─────────────────────────────────────────────────────────────┤
│ ⑤ 决策与提醒层  Decision & Alert                            │
│   规则引擎（止损/止盈/仓位/信号合并）→ 去重 → 分级推送       │
│   通道：托盘通知 / 置顶行情条 / 声音 / 应用内预警中心        │
├─────────────────────────────────────────────────────────────┤
│ ④ AI 推理层  LLM Agent Layer                                │
│   多角色 Agent 编排（技术/资金/基本面/量化/多空辩论/风控）   │
│   结构化输出 + 置信度 + 证据引用（含数据时间戳）             │
│   分级模型路由：快思考（小模型高频）/ 慢思考（大模型复盘）   │
├─────────────────────────────────────────────────────────────┤
│ ③ 量化信号层  Quant Signal Engine                           │
│   因子计算 → 打分 → 概率输出 → 历史校准                     │
│   技术指标 / 量价形态 / 资金流 / 波动率状态                 │
├─────────────────────────────────────────────────────────────┤
│ ② 特征与指标层  Feature & Indicator                         │
│   指标库（MA/MACD/RSI/KDJ/BOLL/ATR/量比…）+ 复权处理        │
│   时序对齐、缺失填充、跨周期聚合（分时→日→周）              │
├─────────────────────────────────────────────────────────────┤
│ ① 数据接入层  Data Ingestion                                │
│   现有 sina/tencent 适配器（复用）                          │
│   + akshare-rs（东财/腾讯/新浪，K线/资金流/财务）           │
│   + 同花顺问财（自然语言选股，可选）                        │
│   + 资讯源（快讯/公告/研报摘要）                            │
└─────────────────────────────────────────────────────────────┘
                        ↕ SQLite（本地持久化）
```

**关键设计原则：**

1. **量化层不依赖 AI，AI 层依赖量化层。** 指标和概率必须由确定性代码算出；LLM 只负责「把数字翻译成人话 + 结合资讯做情景解释」。这样 AI 挂了系统照样能用。
2. **AI 层永远不产生交易动作，只产生「带条件的建议」。** 例如「若明日高开 >1.5% 且量能放大，则趋势确认」——条件由规则引擎校验后才推送。
3. **一切结论必须可追溯。** 每条结论携带：用了哪些数据、数据时间戳、触发了哪个规则、置信度几何。

## 5. 重点：同花顺数据怎么拉（三条路线）

这是你需求里技术风险最高的一块，必须说透。

### 路线 A：同花顺问财 iwencai（自然语言选股）— 你要的「AI 拉数据」

**是什么**：`iwencai.com` 支持中文自然语言查询，例如「今日放量突破20日均线且市盈率小于30的股票」，直接返回结构化表格。这是同花顺自己的 AI 能力，最贴近你的设想。

**技术难点（务必知道）**：
- 请求需要 `hexin-v` 令牌 + 登录 Cookie，`hexin-v` 是**前端 JS 动态生成的**，不是固定值
- 参考实现 `pywencai`（Python）内部依赖 **Node.js 执行 JS** 才能算出这个令牌
- Cookie 有效期通常 7~30 天，过期需重新获取
- 有风控：高频调用会被限流封禁，建议查询间隔 ≥ 2 秒

**在 Tauri (Rust) 里怎么落地**，三个选择：

| 方案 | 做法 | 评价 |
|---|---|---|
| A1 内嵌 JS 引擎 | 用 `boa_engine` / `rquickjs` 在 Rust 里执行 `hexin-v` 生成 JS | 纯 Rust 无窗口，但要重编译约 1 小时且需长期维护令牌 JS |
| A2 复用 WebView2 | 隐藏窗口加载 iwencai 页面，让页面自己的 JS 算令牌，取 cookie 里的 `v` | **rev.2 改为推荐**：零新增依赖、不怕令牌轮换。见 5.2 |
| A3 打包 Node 侧车 | 直接调 `pywencai` | 最省事但引入 Python+Node 运行时分发负担，**不推荐** |

> 💡 rev.2 修正：A1 在纸上更干净，但实测那份 JS 是 **52KB 混淆代码且依赖 jsdom（需要真实 DOM）**，
> 并不能"移植进 Rust 后就是纯函数"。所以改推 A2。详见 5.2。

### 路线 B：同花顺 iFinD（官方付费）

稳定、合规、有正式 API 和 MCP 接口。缺点是要付费采购。**适合产品化后作为付费数据源。**

### 路线 C：东财/腾讯/新浪（等价数据）— 建议作为主力

`akshare-rs` 覆盖这些源的行情、K 线、资金流、财务、板块、龙虎榜。

> ⚠️ **rev.2 重要修正**：原文写的是「这些源无 Cookie、无风控、可直接 Rust 调用」。
> **实测不成立** —— 东财的 `clist` / `push2his` 会被间歇性阻断，新浪列表接口按 IP 限流。
> 另外 `akshare-rs` 的 `stock_zh_a_spot_em()` **只能拿 100 条**，不能用于全市场扫描。
> 真实可用性以 **5.1 节**为准。

### 建议的组合策略（rev.2 按实测修订）

```
全市场快照：东财 clist（字段最全）  ←→  新浪列表（兜底，并发压到 2）
日K：      腾讯 前复权（主力）      ←→  新浪（覆盖最全，北交所唯一可用）←→ 东财
```

### 5.1 实测：各数据通道的真实可用性（2026-09-13，rev.2 新增）

⚠️ **这一节是本方案里最该先看的部分。** 上面那些"建议组合"是纸面推演，
下面是当天用 curl + Rust + Python 逐条打出来的结果。**结论和纸面推演差别很大。**

#### 5.1.1 东方财富：不是"限流"，是两条关键路径被针对性阻断

| 接口 | 结果 |
|---|---|
| `push2.eastmoney.com/api/qt/clist/get`（全市场快照唯一入口） | **HTTP 000，TLS 重协商后断连** |
| `push2his.eastmoney.com/api/qt/stock/kline/get`（日K） | **HTTP 000，同样断连** |
| `push2.eastmoney.com/api/qt/stock/get`（同域单只行情） | ✅ 200 正常 |
| `quote.eastmoney.com` / `datacenter-web.eastmoney.com` | ✅ 200 正常 |

**同一个域名下，只有 `clist` 和 `push2his` 两条路径不通**，其余正常。
后来这两条又自行恢复过 —— 说明是**间歇性阻断**，不是永久封禁。

> **这条结论推翻了原先的假设**：不是"IP 被限流所以要控制频率"，
> 而是"路径会被掐断，所以必须有等价通道"。

#### 5.1.2 新浪：列表接口是**IP 级限流**，日K 接口没问题

| 接口 | 结果 |
|---|---|
| `vip.stock.finance.sina.com.cn/.../Market_Center.getHQNodeData`（全市场列表） | 200 ✅ → **拉满 56 页后变成 HTTP 456「拒绝访问」** |
| 同一个 IP 用 curl 再试 | **也变成 456** → 是本机 IP 被封，不是请求头差异 |
| `money.finance.sina.com.cn/.../CN_MarketData.getKLineData`（日K） | ✅ 稳定，且 `datalen` 可到 3000 |

> 它的日K 在**另一个域名**上，不受影响 —— 这是"同一家数据商、不同子域限流策略不同"的典型例子。

#### 5.1.3 腾讯：日K 是本项目当前的主力通道

| 接口 | 结果 |
|---|---|
| `web.ifzq.gtimg.cn/appstock/app/fqkline/get`（前复权日K） | ✅ 稳定，覆盖沪深创科 |
| 同上 · 北交所 | ⚠️ **只返回 1–2 根**（键名也从 `qfqday` 变成 `day`） |
| `proxy.finance.qq.com/.../rank/pt/getRank`（榜单） | ❌ 200 但 body 为空 |

> 腾讯日K 的字段口径（前复权 + 成交量按手）**与原东财完全一致**，所以换上去之后
> 指标与打分的计算不需要任何调整。北交所必须靠新浪补。

| 源 | 结果 |
|---|---|

#### 5.1.5 最终确定的数据层结构

| 数据 | 主力 | 兜底 |
|---|---|---|
| 全市场快照 | **东财 `clist`**（字段最全，含量比，扛 6 路并发） | 新浪列表（**并发降到 2，遇 456 立即停止**） |
| 日K | **腾讯 前复权** | 新浪（覆盖最全，北交所只有它有）→ 东财 |

配套的两条实现约束（已写进代码）：
1. **通道判定不能只看「非空」，要看「根数够不够」** —— 腾讯给北交所只回 1–2 根，
   按"非空"判定会误判成功，然后打分报"K线不足"。现取 `≥60 根` 为够用。
2. **字段能力要显式建模** —— 新浪列表**没有「量比」**，而 4 套内置预设全都带量比条件。
   若照常比较 `0 < min` 会把结果全部筛空。现在用 `FilterCapabilities` 在字段缺失时**跳过该条件**，
   并把"已忽略的条件"回传给 UI 明确提示。

> 网易/同花顺暂不接入：前者直接不可用，后者北交所缺失且要多请求拼历史，价值不如现有三通道。

### 5.2 问财 `hexin-v` 令牌的实测情况

- 参考实现已拿到（`zsrl/pywencai` 的 `hexin-v.js`，52KB 混淆 JS，**依赖 jsdom** 即需要真实 DOM 环境）
- 实测 `iwencai.com/customized/chart/get-robot-data` → **401**（缺令牌）
- 实测 `unifiedwap/unified-wap/v2/result/get-robot-data` → **403**（nginx 层拦截本机 IP）
- 首页与结果页 HTML 能 200 打开，但**服务端不下发任何 cookie** —— 令牌确实由前端 JS 动态生成

**两条候选路线**（推荐前者）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A2 隐藏 WebView** | Tauri 已有 WebView2，开一个 `visible(false)` 窗口加载问财，让页面自己的 JS 算令牌，再取 cookie 里的 `v` 给 reqwest 用 | **推荐**。零新增 Rust 依赖、不怕令牌轮换。难点是远程页面调用 Tauri 命令需要配 `capability.remote.urls` 白名单 |
| A1 内嵌 JS 引擎 | `boa_engine` 执行那 52KB JS + DOM 模拟 | 纯 Rust 无窗口，但全量重编译约 1 小时，且令牌 JS 会随站点更新轮换，需长期维护 |

> ⚠️ 无论哪条路，**都必须在用户机器上端到端验证一次**才能算数 ——
> 目前 401/403 的迹象说明这台机器访问问财本身就受限。
> **在验证通过之前，不要把问财设成任何主流程的依赖。**

#### 5.3.3 已知限制（写代码前必须知道）

1. **通配符不支持"全市场单日"批量**：`日k:*:20260911` 返回 0 条（`*` 只能作代码前缀，如 `600*` 也不行）。
   全市场批量需**枚举代码**（实测约 2ms/只，7000 只约 15 秒，离线可接受）或用 Python SDK 的
   `rd.get_data(codes=7000)` 批量接口（阶段 B 走 Python 后端时优先用这个）。
2. **响应是 MessagePack**：Rust 侧直连需加 `msgpack`/`rmp` crate 解码；Python 侧 `pip install msgpack`。
3. **引擎是可选外部程序**：本地历史数据默认关闭；用户启用并自动查找或浏览选择 `stockdb.exe` 后，由 Bull Arrives 随应用启动并只管理自己拉起的实例。
4. **数据来自第三方镜像**：准确性需抽样与现有在线通道比对（茅台/平安/一只北交所票，各抽几天与腾讯/新浪对照）；版权与再分发条件由数据源决定。
5. **更新依赖增量同步**：顶部“更新本地数据”入口会停止 owned stockdb、显示同目录 `数据更新.exe`，程序退出后恢复服务；离线时已同步数据仍可用（本地优先）。

#### 5.3.4 分工定案（回答"哪些用它、哪些不用"）

| 场景 | 数据来源 | 理由 |
|---|---|---|
| **已有功能**（实时行情/盯盘/提醒/筛选/推荐/评分） | 在线多通道（**不变**） | 实时性是硬需求；本地库是盘后快照，替代不了 |
| **回测 / 因子检验 / 历史推算**（阶段 B） | **本地 stockdb** | 批量历史查询在线 API 会被限流断联；本地零网络、毫秒级、可重复 |
| **形态识别 / 分时聚类**（阶段 B） | **本地 stockdb 的分钟K** | 全历史分钟线在线根本拉不动 |
| **AI 分析的历史上下文**（阶段 C） | **本地 stockdb**（自带 MCP，Agent 可直连） | 省成本、免限流 |
| **每日增量** | 在线通道 / `数据更新.exe` | 收盘后同步当天 |

**在线 API 的角色收缩为两个**：实时行情 + 每日增量。其余批量历史需求全部本地化。

## 6. AI 层设计：多 Agent 分工

这是本方案最有价值的部分，也是最值得借鉴开源项目的地方（TradingAgents / ai-hedge-fund 都验证了这套分工）。

### 6.1 角色分工

| Agent | 输入 | 输出 |
|---|---|---|
| **数据管家** | 股票代码、日期 | 完整数据包（行情/K线/资金流/财务/资讯）+ 数据完整性标记 |
| **技术分析师** | K线、指标 | 趋势状态、关键位（支撑/压力）、形态识别、量价配合度 |
| **资金分析师** | 资金流、龙虎榜、北向 | 主力动向、筹码状态、资金一致性 |
| **资讯分析师** | 快讯、公告 | 事件影响评级（利好/利空/中性 + 强度 + 时限） |
| **基本面分析师** | 财务指标 | 估值位置、成长性、风险点 |
| **量化模型官** | 因子向量 | 概率输出、期望收益、最大不利偏移（**由代码算，不由 LLM 算**） |
| **多空辩论** | 上述全部 | 正方/反方各自论证 + 反驳，输出「分歧点」 |
| **风控官** | 仓位、波动率、相关性 | 仓位上限、止损位、止盈位、是否一票否决 |
| **组合经理** | 全部 | 最终结论：方向 + 概率 + 触发条件 + 失效条件 |

### 6.2 关键工程约束（不做这些必然翻车）

1. **结构化输出强制**：所有 Agent 输出 JSON schema，用 serde 反序列化校验。禁止自由文本 → 正则解析。
2. **证据引用**：每条判断必须附「依据字段 + 数值 + 数据时间戳」。防止 LLM 编造「MACD 金叉」而实际没有。
3. **量化优先**：概率、指标、关键位由代码算好**塞给** LLM，LLM 不许自己算数。
4. **分级模型路由**：廉价的快思考小模型做高频扫描筛选，昂贵的大模型只在「有信号」时做深度分析。**这一步能把 API 成本降一个数量级。**
5. **全异步 + 超时 + 降级**：LLM 调用必须带超时，失败时降级为「纯量化结论」，绝不能阻塞 UI 或调度器。
6. **幂等与缓存**：同一标的同一时点不重复调用，结果缓存入库。

### 6.3 成本控制（这是能否长期跑下去的关键）

盘中每 5 分钟对 50 只自选股全量跑多 Agent = 成本失控。

正确姿势：
```
每分钟：纯代码算指标/因子（0 成本）→ 命中规则才进入下一步
有信号：小模型做 1 次快速研判（低成本）
高置信信号：大模型做完整多 Agent 深度分析（高成本，但频次低）
盘后：全量深度分析 + 复盘（可接受的高成本时段）
```
再叠加：本地小模型（Ollama / candle / mistral.rs）承担快思考环节，云端大模型只做慢思考。

## 7. 时序编排：盘前 / 盘中 / 盘后

直接挂在你现有的 `market_clock` 状态机上：

### 盘前（09:00 – 09:25）
```
拉隔夜外盘 + 大宗 + 关键资讯
→ 自选股 & 关注池批量快筛
→ 生成「今日策略卡」：市场情绪温度、关注方向、关键价位、当日风险事件
→ 落库 predictions（待次日验证）
```

### 盘中（09:30 – 11:30 / 13:00 – 15:00）
```
定时扫描（默认 5 分钟，可配）
→ 纯代码算因子/信号 → 规则命中？
→ 命中则触发 AI 研判 → 分级推送
监控规则独立线程：止损/止盈/突破/放量 立即触发（不等 AI）
```
**注意：止损止盈这类风控提醒绝不能经过 LLM，必须由代码直接触发。** 延迟差 3 秒可能就是真金白银。

### 盘中异动（事件驱动，秒级）
```
行情推送 → 量价异动检测 → 「即将走出上涨趋势」的多条件确认
（如：放量 1.5 倍 + 突破日内高点 + 均线多头 + 板块同步）
→ 命中即提醒
```

### 盘后（15:00 – 17:00）
```
全量复盘：今日信号命中率、预测偏差、规则触发统计
→ 明日预测（每只持仓/自选：方向、概率、期望收益、关键位）
→ 生成日报（AI 解读 + 图表）
→ 写入预测快照，供次日验证
```

### 夜间 / 周末
```
因子有效性检验（IC / 分层回测）
预测校准（真实胜率 vs 声称置信度）
模型参数更新、策略淘汰
```

### 资讯通知与 AI 推荐：可行性与落地顺序（2026-09-13 讨论定稿）

用户问题："盘中关键资讯通知到我"和"AI 分析后做推荐"可行吗？对现在有帮助吗？

**结论先行：资讯通知（规则版）现在就能做且立刻有用；AI 推荐方向正确但现在做没有地基，必须排在本节末尾的顺序里。**

**第一层：资讯通知 · 规则版（现在就做，零 AI 依赖）**

- 通知管道**早已存在**：monitors / price_alerts + 桌面提醒窗 + 提醒记录。资讯只是**多一类事件源**，
  后端加一个资讯轮询器 + 过滤规则即可，Rust 直做，不需要 Python / AI。
- 资讯源候选（**全部需要先冒烟实测**，按 5.1 的方法论，别信文档）：
  新浪 7x24 快讯流、东财快讯与个股新闻、巨潮公告（有公开接口）、财联社电报（无官方 API、反爬强，最后考虑）。
- 过滤规则（决定打扰程度的生命线）：
  ① **代码匹配**——只推自选股/持仓/监控池相关的；② **类型白名单**——公告（业绩预告/增减持/回购/
  停复牌/重大合同）、涨跌停与龙虎榜、行业政策；
  ③ **通知分级**——关键类才弹桌面提醒，一般类进「提醒记录」静默聚合（与 v1.1.0 零打扰理念一致）。
- 已知风险：资讯源与数据源一样会限流/改版/断联，必须做成**可降级**（源挂了不影响行情与监控）。

**第二层：AI 资讯分级与摘要（AI 薄适配层真连上模型之后）**

- 只对**规则命中**的资讯调用小模型：重要性分级（1–5）+ 一句话影响摘要 + 关联标的确认。
  快讯是短文本，token 成本极低，正好符合 6.3 的"规则命中才进 AI"。
- 输出进通知（"【重要】XX：获 5.2 亿合同，预计增厚明年利润 8%"），深度分析仍要点进详情才触发。

**第三层：AI 分析 → 推荐（阶段 C，三个硬前提缺一不可）**

1. **stockdb 数据验证完成**（阶段 B 第一步）——AI 分析的上下文必须来自验证过的数据，
   否则分析得再好也是垃圾进垃圾出。
2. **多 Agent 框架按 6.2 约束跑通**——量化优先、证据引用、结构化输出；AI 推荐里出现的每个数字
   都必须能追溯到代码算出的指标。
3. **预测落库复盘先跑起来**（第 8 节）——没有"命中率 vs 声称置信度"的统计之前，
   任何推荐都是玄学。**先证明 AI 说的准不准，再让推荐主动出现在你面前。**

且顺序上**先做盘后推荐、后做盘中推荐**：盘后推荐可验证、成本低、时间充裕；
盘中推荐的增量价值是"及时"，但它的错误代价也最高（盘中情绪化决策）。

**落地顺序（写死，防止跳步）**：

```
规则版资讯通知（现在） → AI 接入跑通（阶段 A/C） → stockdb 数据验证（阶段 B 第一步）
→ AI 资讯分级/摘要 → 盘后 AI 推荐 + 复盘闭环 → 盘中 AI 推荐（最后）
```

## 8. 预测闭环：把「玄学」变成「可迭代系统」

**这是整个方案里最重要、也是最多人会跳过的一环。**

没有闭环，你的「AI 预测」永远无法判断好坏。有了闭环，系统会自己变强。

```
每次预测必须落库：
  { 标的, 周期(1日/3日/5日), 方向, 概率, 期望收益, 最大不利偏移,
    置信度, 依据快照, 模型版本, 预测时间, 验证时间 }

次日自动比对：
  实际收益 vs 预测 → 记录 hit / miss

周期性统计：
  ├─ 整体命中率（按周期/按行业/按信号类型分组）
  ├─ 校准曲线：声称 70% 的预测，实际命中率是多少？
  └─ 盈亏比与期望值

用校准结果反哺：
  ├─ 概率打折（若声称 70% 实际只有 55%，全局校准）
  ├─ 淘汰无效因子 / 无效信号类型
  └─ 动态调整各 Agent 在最终结论中的权重
```

**具体建议**：前 2~4 周只做「记录 + 统计」不做任何调参，先攒够样本。没有 200+ 条预测样本，任何胜率数字都没有统计意义。

## 9. 技术选型

### 9.1 Rust 侧依赖

| **MCP** | `rmcp` | MCP 官方 Rust SDK，已在你构建工具链版本范围内 |
| **技术指标** | 自研 + 参考 `ta-rs` | 指标计算简单，自研可控性更好（复权、停牌、涨跌停处理需定制） |
| **本地小模型**（可选） | `mistral.rs` / `candle` | 承担快思考环节，省 API 成本 |
| **密钥加密** | OS Keychain | **API Key 绝不能明文存 SQLite** |

> ⚠️ **注意 `rig` 目前是 0.x**，官方明确预告会有破坏性变更。建议锁定小版本号（`=0.42.x`），升级前看 changelog。

> ⚠️ **关于 akshare-rs 的实测修正**：它的 `stock_zh_a_spot_em()` **只能拿 100 条**
> （`pn` 被硬编码为 1），**不能用于全市场扫描**，必须自建适配器 ——
> 这一点已在 `datasource/eastmoney_universe.rs` / `sina_universe.rs` 落地。
> 另外 reqwest 本身要显式 `.no_proxy()`，否则系统代理会切断国内数据源的 TLS（见 5.1.1）。

### 9.2 Rust 内置 vs Python 外挂：分界定案（rev.2 重写）

> rev.1 的结论是「产品保持纯 Rust 单二进制，Python 只做你自己的离线模型工坊」。
> 经过讨论与**实测**（见 9.2.3 的体积数据），改为下面这套更细的分界。

#### 9.2.1 分界准则

不是「Python 更强所以都给它」，而是按这三条切：

| 特征 | 归属 |
|---|---|
| 需要**常驻 / 低延迟 / 单文件分发** | **Rust** |
| 需要**现成的科学计算或财经数据生态** | **Python** |
| 只是**一次 HTTP 调用**（如调大模型） | **Rust 也行** —— 别为了它单独引入 Python |

#### 9.2.2 逐功能归属

| Rust 内置（**不该**外置） | Python 研究后端（**该**外置，按需拉起） |
|---|---|
| 行情轮询 / 盯盘 / 提醒触发 | 回测（T+1、涨跌停、复权）→ RQAlpha / vectorbt |
| 指标 MA/MACD/RSI/KDJ/BOLL/ATR | 因子有效性检验（IC/IR）、ML → sklearn / lightgbm |
| 多因子打分、全市场筛选、推荐榜 | 形态识别 → stumpy(Matrix Profile) / tslearn(K-Shape) |
| 日K 多通道适配 | **历史数据底座：本地 stockdb**（2019 起日K + 2025 起分钟K + 复权因子，见 5.3） |
| SQLite 落库、UI、通知 | AI 编排（多模型、多 Agent、RAG、prompt 管理） |
| — | 长尾数据：**优先 stockdb more-power 版**（官方称含财务/期货/债券/因子/ticks，覆盖待验证），缺项再用 akshare 在线补 |

**为什么盯着"常驻/低延迟"而不是"难不难"**：盯盘和提醒要毫秒级响应、要能开机就挂着、
要以单个 exe 分发。放 Python 会引入进程常驻 + GIL + 内存占用 + 启动延迟 ——
为了它养一个 200MB 的运行时，不划算。
反过来，回测/因子/形态识别是**生态碾压**，不是语言之争；在 Rust 里从零写一个正确处理
T+1、涨跌停、复权的回测框架是几个月的活。

**筛选器为什么不外置**：它现在是「拉一次全市场快照 + 内存筛选」，**零额外网络请求**、毫秒级完成。
外链化只会更慢更难用。

#### 9.2.3 外置的实测成本

| 项 | 体积 |
|---|---|
| Python 3.13 解释器本体 | 53 MB |
| `pandas` + `numpy` 的 site-packages | 约 100 MB（pandas 67 / numpy 34 / numpy.libs 21） |
| **合计** | **约 215 MB**（再上 sklearn / torch 会到 GB 级） |

所以外置要提前认下三个代价：**体积膨胀**、**进程管理**（拉起/退出/端口/僵尸进程）、
**两套运行环境**（用户自装 Python，或你打包成单文件 exe）。

#### 9.2.4 推荐的链路（修正一个常见误解）

❌ 常见设想：`Bull 调用 Python → Python 算完返回 → Bull 再用 AI 分析`

问题：**AI 分析需要的上下文（指标序列、形态、财务、资金流）Python 侧已经全算好了**，
让 Bull 拿回来再重组一遍是重复劳动；而多 Agent / 工具调用 / RAG 的生态也在 Python。

✅ 推荐链路：

```
Bull（Rust）                        Python 研究后端
   │                                    │
   │  ① 意图 + 标的（JSON）             │
   ├───────────────────────────────────>│
   │                                    │  ② 取数 + 计算
   │                                    │  ③ 喂模型（AI 编排在这里）
   │  ④ 结构化结论（JSON）              │
   │<───────────────────────────────────┤
   │                                    │
   │  ⑤ 落库 + 通知 + 展示               │
   ▼                                    ▼
```

**例外**：如果 AI 只是"单模型、单轮、上下文就是现有那 17 个指标"，
放 Rust 完全够（`reqwest` 发个 POST 就行），**不必为此引入 Python**。先做这个版本成本最低。

#### 9.2.5 四条铁律

1. **核心功能绝不依赖 Python**。没装 Python 时，行情、盯盘、提醒、指标、筛选全部照常，
   只有「研究台」入口置灰并给出安装指引。
2. **Python 不写 SQLite**。落库统一由 Bull 做，避免两个写入者争库。
3. **别用 stdin/stdout 传数据**（易碎、中文编码有坑）。用**本地 HTTP + JSON**；
   回测这类长任务必须走**任务队列 + 进度轮询/SSE**，否则一定超时。
4. **按需拉起、空闲自动退出**，端口写到临时文件让 Bull 读取。

#### 9.2.6 通信与集成的演进路径

```
现在    Rust 内部调用（AI 薄适配层）
         ↓
第二步  本地 HTTP + JSON（Python 研究后端，Bull 单向调用；
        历史数据由本地 stockdb 提供，Python 侧经 SDK/msgpack 取数，见 5.3）
         ↓
第三步  MCP（AI Agent 直接调工具）
        stockdb **自带 MCP**（无需装 SDK）→ Agent 可直接查历史行情/复权/分钟线；
        Python 侧再暴露计算能力（回测/因子/形态）
```

注意 stockdb 的 MCP 是**自实现协议**（README 声明"无需额外安装 MCP SDK"），
与标准 MCP 客户端的兼容性需要在阶段 C 实测后再定；不通就退回 HTTP API（已实测可用）。

### 阶段 B · Python 研究后端（数据底座：本地 stockdb，见 5.3）

- ⬜ 回测引擎（数据从 stockdb 取；务必处理 T+1 / 涨跌停 / 复权 / 手续费滑点）

- ⬜ 因子有效性检验（IC / IR / 分层回测）—— 全市场七年日K本地毫秒级，不再受在线限流约束
- ⬜ 形态识别（Matrix Profile / K-Shape），对应早前那三张 KMeans 图的升级路线
  （**本地分钟K 2025-01-02 起、单票 9.9 万根，147ms 取全年**——在线方案完全不可行）
- ⬜ 长尾数据（财务 / 资金流 / 龙虎榜 / 北向）：**先验证 stockdb more-power 版的覆盖**

**验收**：没装 Python 时内置功能完全不受影响；装上后能跑通一次完整回测并产出报告，

## 11. 风险清单与合规提醒

### 技术风险
| 风险 | 应对 |
|---|---|
| **数据源路径被间歇性阻断**（东财 `clist`/`push2his` 实测 HTTP 000） | **必须有等价通道 + 多通道回退**（见 5.1）；不能只依赖单一数据商 |
| **列表接口 IP 限流**（新浪拉满 56 页后 HTTP 456，连 IP 被封） | 并发压到 2；识别 456 后**立即停止派发剩余页**；优先用不限流的通道 |
| **数据源字段缺失**（新浪列表无量比，而预设全都带量比条件） | 显式建模"字段能力"，缺失时**跳过该条件**并把事实回传给 UI，不能拿 0 去比较 |
| **通道返回数据过短被误判成功**（腾讯给北交所只回 1–2 根） | 判定标准用「根数够不够」而非「非空」；全都不够时返回根数最多的那个 |
| 同花顺 Cookie / `hexin-v` 令牌失效或 IP 被拦 | 问财仅作增强，**验证通过前不进任何主流程**（见 5.2）；主链路用东财+腾讯+新浪 |
| **用户实际运行的不是最新构建** | 设置 → 系统显示「版本 / 构建时间 / 程序路径」，一眼可核对 |
| LLM 幻觉编造技术指标 | 指标由代码算好塞给它；强制证据引用校验 |
| API 成本失控 | 分级模型路由 + 缓存 + 仅信号触发才深度分析 |
| LLM 阻塞 UI / 调度器 | 全异步 + 超时 + 降级为纯量化结论 |
| 前视偏差导致回测虚高 | 严格时间戳对齐，只用 T 时刻及之前的数据 |
| `rig` 0.x 破坏性变更 | 锁定小版本 |
| **前端表格渲染空白被误判为"没数据"** | 结果表不用 `virtual-scroll`（容器高度算成 0 时会整体空白）；空态要有明确文案 |

### 合规风险（请务必重视）
1. **投资建议资质**：在境内，向公众提供证券投资建议需要持牌。**个人自用无妨，一旦对外发布/收费，法律风险很高。**
2. **免责声明**：产品内必须显著标注「本工具仅供研究与学习，不构成投资建议，据此操作风险自负」。
3. **数据合规**：爬取第三方数据可能违反其服务条款，注意频率控制与使用范围。
4. **API Key 安全**：必须加密存储，不得上传、不得写日志明文。

|---|---|

   封装全市场批量取数（`rd.get_data(codes=7000)`），并做引擎的探测/拉起。
   之后再搭 Python 骨架，逐个接回测 / 因子 / 形态。
   历史与批量数据一律走本地（零网络、零限流），在线 API 只保留实时行情与每日增量。

3. **阶段 C —— 预测闭环 + 多 Agent**
   这是长期护城河，但必须建立在稳定的数据与规则之上。

> **一句话总结分界**：边界划在**「常驻 vs 重活」**，不是「难 vs 不难」。
> 筛选器留在 Rust（零额外请求的内存筛选），回测和 AI 编排交给 Python。
